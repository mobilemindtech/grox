# Modularização

Plano para separar o framework em módulos, com um núcleo sem Grails (Groovy + atores + Netty), uma camada de compatibilidade com o Grails, outra com os plugins do Grails e, no futuro, um projeto com DSL própria (rotas mais simples, sem o layout `grails-app/`) que use os módulos de GORM e GSP.

Status: fases 1 a 4 concluídas: o framework está em subprojetos `framework/grox-*`, o atendimento HTTP é do core e o `sample-plain` roda sem o módulo Grails (core + gorm + gsp + security + `grox-dsl`). Próximo: a DSL de projeto e de HTML. Branch `modularizacao`. Checklist no [roadmap](roadmap.md#modularização).

## Módulos-alvo

| Módulo | Conteúdo | Depende de |
|---|---|---|
| `grox-core` | Atores, Netty, http (`GroxRequest`/`GroxResponse`/`GroxParams` puros), sessão (memória/Redis), config, roteamento genérico, i18n, `ContextPropagation`, management, async, services-ator, recarga, SPI `GroxModule` | |
| `grox-gorm` | `org.grox.data.*`, API do GORM (`grails.gorm.*`, `org.grails.datastore.*` menos `...multitenancy.web`, `org.grails.orm.*`), `grails.validation`, shims de transação/validação do Spring, binding (`org.grox.data.binding.DataBinder`), `WhereQueryTransformation` | core |
| `grox-gsp` | Motor GSP, SiteMesh, `TagLibRegistry`, tags `g:` genéricas | core |
| `grox-assets` | Asset pipeline | core |
| `grox-security` | Motor de segurança (filtro, regras, JWT, CSRF, bcrypt) e os pontos de extensão (`PasswordCodec`, `SecurityListener`, `AccessRuleSource`, `TokenStore`), sem os nomes do Grails/Spring (exceto as interfaces `Authentication` e `GrantedAuthority`, ver decisões) | core |
| `grox-security-gorm` | `org.grox.security.gorm`: usuários e tokens em domain classes, tenant do usuário logado | core, gorm, security |
| `grox-grails` | Controllers, `ControllerApi`, `UrlMappings`, interceptors, AST do layout `grails-app/`, fachadas servlet/Spring, `grails.*` da web, `Environment`, `GrailsApplication` | core, gorm, gsp, assets, security, security-gorm |
| `grox-grails-plugins` | `org.grox.plugins.*` (console, quartz, excel, redis, rabbitmq, auditlog, rendering) e as APIs originais (`grails.plugin.springsecurity.*`, `org.springframework.security.*`, `asset.pipeline.*`, `pl.touk.*`, `com.budjb.*`, `groovyx.gpars.*`) | todos acima |
| `framework` | Agregador (`api` de todos): sample-app e candidatos não mudam | todos |
| `grox-dsl` | Rotas por closure e por anotação, respostas no estilo Grails, `@Handler` | core, gorm, gsp, security |
| `grox-pug` | `org.grox.pug`: views `.pug` (pug4j) com expressões em Groovy e TagLibs como elementos | core, gsp |
| `grox-markdown` | `org.grox.markdown`: views `.md` (GSP + commonmark) e `<md:render>` | core, gsp |

Decisões:
- A API do GORM continua nos pacotes `grails.gorm.*`: é a API pública do GORM (que também roda fora de uma app Grails). "Sem Grails" vale para a web e para a estrutura do projeto, não para o nome do pacote do GORM. Uma domain class fora de `grails-app/domain` é reconhecida pela interface `GormEntity`.
- Os pacotes não são renomeados, e nenhum pacote fica dividido entre dois jars (o mapa do `ArquiteturaTest` é só por pacote, e ele confere que cada fonte está no subprojeto do seu pacote).
- As interfaces `org.springframework.security.core.Authentication` e `GrantedAuthority` (contratos de poucos métodos, sem lógica nem dependências) contam como API do `grox-security`: a autenticação do Grox as implementa para o código tipado das apps (`Authentication auth = springSecurityService.authentication`) continuar valendo. O resto da API do spring-security fica no plugin.
- As interfaces servlet (`jakarta.servlet.http.*`) e os marcadores `MultipartFile`, `MultipartHttpServletRequest` e `GrailsParameterMap` contam como API do `grox-core`: o http os implementa para as assinaturas tipadas das apps (`HttpServletRequest request`, `def salvar(GrailsParameterMap params)`). Inverter exigiria fábricas nos pontos de criação, inclusive no caminho quente. As interfaces servlet vêm do jar oficial `jakarta.servlet-api` (dependência `api` do core), no lugar das antigas cópias parciais: uma biblioteca que traga o jar não conflita mais com o Grox.
- A configuração da segurança continua em `grails.plugin.springsecurity.*` (só chaves, sem dependência de código). A DSL poderá aceitar um prefixo próprio.
- Também contam como API do core os contratos do Spring sem lógica em `org.springframework.context` (`ApplicationEvent`, `ApplicationListener`, `MessageSource`; o pacote inteiro, para não dividi-lo, sem os subpacotes) e a API de tarefas `grails.async` (`Promise`, `Promises`), que o core implementa. A anotação `grails.events.annotation.gorm.Listener` é do GORM.
- Os plugins Gradle `org.grox.app` e `org.grox.lib` ficam com o `grox-grails` (são do layout Grails). A DSL terá o seu.

## Acoplamentos a desfazer (fase 2)

Levantados pelas referências entre pacotes (lista completa em `framework/src/test/resources/arquitetura-violacoes.txt`, 206 na fase 1):

| Acoplamento | Violações | Solução |
|---|---:|---|
| ~~`GroxRuntime` monta tudo (GORM, GSP, segurança, controllers, plugins)~~ | 75 | **Feito:** SPI `GroxModule` (fases de subida e desligamento, beans), descoberta por `ServiceLoader`; o runtime só orquestra. Cada módulo tem a sua classe (`GormModule`, `SecurityModule`, `GspModule`, `AssetsModule`, `GrailsModule` e os dos plugins). Ainda no `GrailsModule` e a mover para o core junto com o `Handler` genérico: sessões, estáticos, management, access log e cabeçalhos de segurança |
| ~~Segurança implementa as interfaces do spring-security e usa GORM~~ | ~35 | **Feito:** pontos de extensão no motor (`PasswordCodec`, `PasswordUpdater`, `SecurityListener`, `AccessRuleSource`, `TokenStore`, `userSources`), implementados pelo `org.grox.plugins.springsecurity` (exceções do login na sessão, `RestTokenCreationEvent`, `@Secured`, `passwordEncoder`, `principal as GrailsUser` por extensão do Groovy) e pelo novo `org.grox.security.gorm`. O `SecurityFilter` recebe endpoints, destinos, sessões e mensagens do módulo web, e lê a requisição corrente pelo `CurrentRequest` do core |
| ~~`ServiceProxies` aplica `@Transactional`/tenancy do GORM~~ | 11 | **Feito:** `org.grox.service.ServiceInterceptor` por `ServiceLoader`; o GORM registra o `GormServiceInterceptor` (transação e tenant) |
| ~~APIs do Spring e do Grails sem lógica; o core, o GORM, o Grails e os assets referenciam plugins~~ | 12 | **Feito:** classificação dos contratos (ver decisões); `AssetResourceLocator` no novo `org.grox.plugins.assetpipeline` (com o `AssetPipelineModule`); `authenticatedUser` dos controllers como extensão do plugin spring-security; o trait dos jobs registrado pelo quartz (`org.grox.ast.ArtefactTrait`). Sobra o console no `WebContext`, que sai com o `Handler` genérico |
| ~~i18n, `Management` e `AccessLog` conhecem `FieldError`, `Persistence` e a segurança~~ | 6 | **Feito:** `org.grox.i18n.MessageResolvable` (implementada pelo `ObjectError`); verificações do `/health` por `GroxModule.healthChecks` (o GORM dá a `db`); o access log lê `request.userPrincipal`, que o `GroxRequest` resolve pelo atributo `PRINCIPAL_ATTRIBUTE` |
| ~~`GroxApplication` conhece `GrailsApplication`, `GormEntity`, Data Services~~ | 8 | **Feito:** o core guarda as classes por tipo (`ArtefactType`, só `Service` no core) e cada módulo registra os seus em `GroxModule.artefactTypes`; o bean `grailsApplication` (com `mainContext`, `GrailsClass` e `xxxClasses`) é a fachada `org.grox.web.GroxGrailsApplication`, criada pelo `GrailsModule` em `prepare`. O ambiente é do core (`org.grox.core.Env`), e o `grails.util.Environment` delega para ele |
| ~~`GroxRequest` implementa `HttpServletRequest`; `GroxParams` estende `GrailsParameterMap`; o http usa `JSONObject`, `withFormat`, `Formats`, `RequestContext` e `DataBinder`~~ | ~13 | **Feito:** as interfaces servlet e os marcadores (`MultipartFile`, `MultipartHttpServletRequest`, `GrailsParameterMap`) contam como API do core (ver decisões); tipos MIME em `org.grox.http.MimeTypes`, conversões em `org.grox.core.Conversions` (editores do Spring por gancho do `GrailsModule`), sessão por `sessionProvider` do `WebRequest`, `request.withFormat` como extensão do Groovy no módulo Grails e `request.JSON` como `JSONObject` por gancho (`GroxRequest.jsonView`) |
| ~~`ContextPropagation` e `AsyncSupport` conhecem `Persistence`, `Tenants`, `SecurityContextHolder` e `RequestContext`~~ | 7 | **Feito:** `org.grox.core.ContextProvider` por `ServiceLoader`; cada módulo declara os valores dos services-ator e das tarefas e o envoltório da tarefa (sessão de dados sob demanda) |
| ~~Tags `sec:`, `asset:` e de erros na GSP; CSRF no `g:form`~~ | 9 | **Feito:** `org.grox.view.GspContributor`: cada módulo traz as suas TagLibs (`SecurityTagLib` no spring-security, `AssetTagLib`/`AssetMethodTagLib` no asset-pipeline), registradas depois das nativas e antes das da app; o pré-compilador acha os namespaces pelos mesmos módulos. | ~~GSP usa `WebRequest`, `JSON`, `GrailsApplication`~~ | 11 | **Feito:** `org.grox.view.ViewRequest` (estende o `RequestScope` do core: params, flash, sessão, controller/action, links, mensagens, estáticos, views), que o `WebRequest` implementa; `grailsApplication` e `grailsAttributes` das TagLibs da app no trait `org.grox.web.taglib.GrailsTagLibApi` (aplicado pela AST); o import do `JSON` nas GSPs vem do `GrailsModule` (`GspContributor.gspImports`, também no pré-compilador); `encodeAsJSON` por gancho (`CodecExtensions.json`) |
| ~~GORM usa `RequestContext` (JSON) e o `DataBinder`~~ | 9 | **Feito:** `DataBinder` em `org.grox.data.binding`, com os editores da app pelo gancho `Conversions.editors`; `DomainJson.errors` recebe o resolvedor de mensagens (o `JsonSupport` passa o da requisição); `org.grails.datastore.mapping.multitenancy.web` (`SessionTenantResolver`, no GORM do `grails-datastore-web`) é do módulo Grails |
| ~~Roteamento conhece `ControllerArtefact`; segurança conhece `WebContext`, `WebRequest`, `RequestContext` e `Html`; `WebContext` conhece o console~~ | 8 | **Feito:** `org.grox.routing.RouteTarget` (o `ControllerArtefact` é um); `org.grox.http.Endpoint` para os endpoints especiais (`Management`, `WebConsole`), que o `WebDispatcher` e a segurança tratam por lista; `org.grox.http.RequestScope` com o `ScopedValue` no core (`CurrentRequest.VALUE`, o mesmo do `RequestContext`, então sem vínculo extra por requisição); `Html` e `SafeHtml` em `org.grox.http`. Ainda no `GrailsModule`: montar sessões, estáticos, management, access log e o dispatcher (o `sample-plain` vai pedir um dispatcher do core) |

## Fases

1. **Fronteiras verificáveis** (feito): `ArquiteturaTest` mapeia cada pacote para o módulo-alvo e falha com dependência nova ou com violação resolvida que continua na lista (a lista só encolhe). Regravar: `./gradlew :framework:test --tests org.grox.ArquiteturaTest -Darquitetura.atualizar=true`.
2. **Quebrar os ciclos no mesmo jar**, um refactor por vez, cada um com o build verde: SPI `GroxModule` (começando pelo `GroxRuntime`), fábrica de request/params, `Handler` genérico, propagação de contexto por registro, `DataBinder` no gorm, taglibs registradas pelo módulo, tipos próprios da segurança.
3. **Subprojetos Gradle** (feito): os fontes foram para `framework/grox-*` pelo mapa de pacotes do `ArquiteturaTest`, sem renomear pacotes nem dividir nenhum, e o `framework` virou o agregador (`api` de todos) com os testes. Recursos foram com o módulo dono: cada `META-INF/services` tem só as classes do seu jar, e cada jar tem o seu descritor de extension module (`grox-grails-extensions`, `grox-gsp-extensions`...). Os módulos compilam sem as ASTs globais (`framework/gradle/compilador-modulos.groovy`), como antes da divisão. Para isso, o mapa passou a ser só por pacote: `WhereQueryTransformation` foi para `org.grox.data.ast` (ela usava o `artefactDir` da AST do Grails; agora tem a própria checagem do `grails-app/domain`), `org.springframework.security.core` inteiro é do `grox-security` (com o `AuthenticationException`) e `grails.plugins` é do `grox-grails` (os subpacotes são dos plugins).
4. **`sample-plain`**: app mínima com core + gorm + gsp + security, rotas programáticas e sem `grails-app/`. Vira o teste que garante o núcleo sem Grails e a base para desenhar a DSL. Em etapas:
   - (feito) **Pipeline HTTP no core**: o `WebDispatcher` foi dividido. O comum a qualquer app ficou no `org.grox.http.HttpPipeline` (montado pelo `HttpModule`, ordem 50), e o do Grails no `ControllerRouter` (um `org.grox.routing.Router`). A segurança entra como `RequestFilter` (`SecurityRequestFilter`, com a página de login por `LoginView`); estáticos e assets como `ResourceHandler`; o 403 do tenant ausente por `GroxModule.exceptionStatuses`.
   - (feito) **`grox-dsl`**: rotas por closure (`routes { get('/livros') { ... } }`) e por anotação em classe e método (`@Get`, `@Post`), sobre o mesmo roteador. Execução em virtual thread ou em ator: padrão em `grox.routes.execution`, que cada rota ou grupo pode trocar (`group('/relatorios', execution: 'actor', poolSize: 2)`).
   - (feito) **`sample-plain`** com testes de integração (`SamplePlainTest`): sobe sem o módulo Grails no classpath. Para isso, a `ValidationTagLib` voltou à GSP (lê os erros pela API `Errors` de forma dinâmica e traduz pela `MessageResolvable`), o JSON das entidades foi para o GORM (`GormJson`), o pool de atores para o core (`ActorPool`) e as domain classes fora do `grails-app` usam `@grails.gorm.annotation.Entity` (a injeção de `id`, `version` e associações saiu da AST do Grails para o `DomainClassSupport` do GORM). O `CompositeRouter` do core junta controllers e rotas numa mesma app.

## Cuidados

- **Desempenho**: as contribuições dos módulos são resolvidas na partida, em listas fixas; nada de lookup por requisição. Medir com `bench/run.sh` em A/B antes e depois da fase 2.
- **Recarga em desenvolvimento**: a recarga leve passa a perguntar a cada módulo o que ele recarrega.
- **Limite do teste**: ele vê imports e nomes qualificados; referências pelo nome simples dentro do mesmo pacote não contam (só importa nos pacotes com exceção por classe, como `org.grox.ast`).
